我先给明确结论：如果你是完全新手、计划单人或极小团队开发，默认选择应当是：

> Godot 4.x 稳定版 + 类型化 GDScript + Git/Git LFS + PC/itch.io 优先 + 小型 2D 或低复杂度 3D 游戏。

Godot 很适合 AI 辅助开发，但“AI 友好”并不等于“让 AI 一句话生成整款游戏”。真正有效的是：工程文本化、命令行验证、自动测试、运行截图反馈和严格控制范围。

## 1. 引擎选择与 AI 友好度

| 引擎      | 最适合                                   | AI 友好度 | 主要问题                                                     |
| --------- | ---------------------------------------- | --------: | ------------------------------------------------------------ |
| Godot     | 2D、风格化/中小型 3D、桌面/Web、小团队   |      很高 | 主机导出依赖第三方；大型商业插件生态不如 Unity               |
| Unity     | 手机、多平台、成熟商业 SDK、庞大素材商店 |        高 | 更重、更复杂、专有软件；后期可能需要付费                     |
| Unreal    | 高画质 3D、影视化、开放世界、主机        |        中 | 对新手和 AI 都更重；Blueprint、`.uasset` 等大量内容并非纯文本 |
| GameMaker | 快速制作纯 2D                            |      中高 | 商业发布需要购买许可，扩展性不如通用引擎                     |
| GDevelop  | 完全不会编程、想几天内做出原型           |        高 | 内置 AI 和无代码很方便，但复杂项目上限较低                   |

我判断 AI 友好主要看六点：

1. 场景、配置、脚本是否容易让 AI 阅读和修改。
2. 能否用命令行启动、检查、测试、导出。
3. 是否有稳定的错误日志。
4. 是否能自动截图或录制运行结果。
5. 是否有测试框架和版本控制支持。
6. AI 是否能接触真实编辑器状态，而不只是“猜代码”。

Godot 在这些方面表现很好：

- MIT 许可、无版税，游戏本身可以使用任意许可证或商业发行。[Godot 许可说明](https://docs.godotengine.org/en/stable/about/complying_with_licenses.html)
- 官方明确以“可读、可合并”的工程文件为目标，并提供 Git/Git LFS 指导。[Godot 版本控制文档](https://docs.godotengine.org/en/stable/tutorials/best_practices/version_control_systems.html)
- 可以命令行启动编辑器、运行场景、导出、调试和 `--headless` 运行。[Godot CLI 文档](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)
- 完全开源，无引擎使用限制。[Godot 官方介绍](https://docs.godotengine.org/en/stable/about/introduction.html)

需要知道的限制：

- Godot 4 的 C# 项目目前仍不能导出 Web；要做网页游戏，优先选择 GDScript。[Web 导出文档](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- 除 Steam Deck/Linux 外，主机平台通常需要主机 SDK 和第三方移植服务。第一款游戏不建议直接以 Switch、PlayStation 或 Xbox 为首发目标。[Godot 主机支持文档](https://docs.godotengine.org/en/4.4/tutorials/platform/consoles.html)
- Unity 目前个人版在相关收入/融资低于 20 万美元时免费，并已提供 Unity AI、MCP 和 CLI；其商业生态仍然最大。[Unity 定价](https://unity.com/products)
- Unreal 游戏单产品终身收入超过 100 万美元后，一般对超出部分收取 5% 分成。[Unreal 许可](https://www.unrealengine.com/license)
- GDevelop 是开源、无代码并带 AI 的快速原型方案，但云端发布、AI、协作存在套餐限制。[GDevelop 功能](https://gdevelop.io/game-makers)、[定价](https://gdevelop.io/pricing)

因此：

- 你的第一款游戏如果是 2D、卡牌、塔防、轻量动作、解谜、模拟经营：选 Godot。
- 如果是写实 3D、大地图、复杂多人射击：先缩小想法；确实不能缩，再考虑 Unreal。
- 如果目标是重度移动商业化、广告/IAP/第三方 SDK：Unity 更稳妥。
- 如果目前只是想验证一个玩法而完全不想写代码：先用 GDevelop，验证后再决定是否迁移。

## 2. Godot 的高质量 AI Skill／工作流

你的理解是对的：这里的 Skill 指“教 AI 怎样开发 Godot 项目”的规则、流程和辅助脚本，而 MCP 只是让 AI 能操作编辑器的执行接口。

目前还没有一个“Godot 官方、全行业公认”的 AI Skill，但已经有几套很值得研究的公开工作流。

### 最有影响力：Claude Code Game Studios

[Claude Code Game Studios](https://github.com/Donchitos/Claude-Code-Game-Studios) 约 25.3k stars，包含 49 个角色和 73 个工作流 Skill，覆盖：

- 概念和核心循环
- 原型
- 架构和任务拆分
- 垂直切片
- 测试和 QA
- 素材审计
- 性能、发布、补丁和复盘

它的[完整工作流指南](https://github.com/Donchitos/Claude-Code-Game-Studios/blob/main/docs/WORKFLOW-GUIDE.md)把开发分成七个阶段，并设置阶段门槛；[Vertical Slice Skill](https://github.com/Donchitos/Claude-Code-Game-Studios/blob/main/.claude/skills/vertical-slice/SKILL.md)尤其值得读。

优点：过程完整、强调范围控制和可验证结果。
缺点：对第一款小游戏明显过重，而且主要针对 Claude Code。建议吸收其流程，不要一开始把 49 个角色全搬进项目。

### 最适合借鉴自动开发闭环：Godogen

[Godogen](https://github.com/htdt/godogen) 约 7k stars，明确支持 Codex 和 Claude Code。它最有价值的原则是：

> 不以“代码编译成功”为完成，而以实际运行的游戏、截图或视频为依据。

它的 [Godot 指南](https://github.com/htdt/godogen/blob/master/engines/godot.md)定义了构建、导入、场景生成和录屏流程；[运行提示词](https://github.com/htdt/godogen/blob/master/prompts/runtime.md)要求 AI 持续从真实运行结果判断下一步。

不过它默认使用 Godot C# 和 AI 生成资产，更适合作为高级自动化参考，而不是新手教程。

### 低影响力但工程质量很好的 Skill

[headless-godot-skill-kit](https://github.com/abagames/headless-godot-skill-kit) 社区影响力较小，但流程非常实用：

```text
修改
→ 预检查
→ 用 Godot API 修改场景
→ Headless 冒烟测试
→ 逻辑测试
→ Web 导出
```

它强调：

- 不直接手写复杂 `.tscn`
- 固定命令和日志
- 区分“项目能启动”与“游戏逻辑正确”
- 每次修改后重复同一条验证流水线

这是我最建议为你的项目精简改造成 Codex Skill 的基础。

| [Terrain3D](https://github.com/TokisanGames/Terrain3D)       | 大型 3D 地形                      | 只在确实需要室外大地形时安装 |
| [Godot AI](https://github.com/hi-godot/godot-ai)             | AI 操作编辑器和运行反馈           | 基础项目跑通之后安装         |

我的建议是第一周只安装一个测试框架。相机、对话、AI、地形插件都等玩法证明需要时再加入。

选择插件要检查：

- 是否支持你锁定的 Godot 版本。
- 最近是否仍在维护。
- 是否有明确许可证、文档和示例项目。
- 是否支持命令行或自动测试。
- 是否把核心数据存成可读文本。
- 升级前是否能在独立分支验证。

插件越多，AI 需要理解的非标准 API 越多，版本冲突和“插件替你决定架构”的风险也越大。

## 4. 游戏资产究竟包括什么

“游戏资产”远不只是模型。

| 类型         | 例子                                            |
| ------------ | ----------------------------------------------- |
| 2D 美术      | Sprite、Tileset、背景、角色立绘、UI、图标、字体 |
| 3D 美术      | 模型、骨骼、动画、材质、纹理、HDRI、碰撞体      |
| 音频         | 音效、环境音、音乐、语音、混音预设              |
| 视觉技术资产 | Shader、粒子、VFX、后处理、灯光配置             |
| 游戏数据     | 关卡、物品表、对话、任务、数值配置、本地化文本  |
| 技术资产     | 插件、模板、角色控制器、存档系统、编辑器工具    |
| 源文件       | Blender、Aseprite、Krita、PSD、音频工程文件     |
| 商店资产     | Logo、Steam capsule、截图、宣传片、新闻图       |

代码通常被称为源代码或系统，但在素材商店中，插件和模板也会被称为“代码资产”。

## 5. 高质量免费资产来源

优先选择许可证最清晰、风格成套的来源。

### 最安全的一组

- [Kenney](https://kenney.nl/assets)：大量一致风格的 2D、3D、UI、音效和 Starter Kit；官方说明全部素材页资产为 CC0，可商用且不强制署名。[许可说明](https://kenney.nl/support)
- [Poly Haven](https://polyhaven.com/)：高质量 HDRI、纹理和 3D 模型，全部 CC0。[许可](https://polyhaven.com/license)
- [ambientCG](https://ambientcg.com/)：材质、纹理、模型和 HDRI，全部 CC0，可将原始文件包含在游戏里。[许可](https://docs.ambientcg.com/license/)
- [Quaternius](https://quaternius.com/)：风格统一的低多边形模型、角色和动画，很多完整游戏套件为 CC0。例如其 [Platformer Kit](https://quaternius.com/packs/ultimateplatformer.html)。
- [Sonniss GameAudioGDC](https://sonniss.com/gameaudiogdc/)：大型专业音效包，可商用、免版税、无需署名，但不能把声音作为独立素材包重新分发；当前许可证还禁止用于 AI 训练。[许可证](https://sonniss.com/gdc-bundle-license/)

### 数量很大，但每个素材都要单独检查

- [itch.io 免费游戏资产](https://itch.io/game-assets/free)：质量和风格非常丰富，但每个作者许可证不同。
- [OpenGameArt](https://opengameart.org/)：2D、3D、音乐和音效；可能是 CC0、CC BY、CC BY-SA、GPL 等，必须逐项处理署名和传染性要求。[许可 FAQ](https://opengameart.org/content/faq)
- [Freesound](https://freesound.org/)：音效巨大，但包含 CC0、CC BY 和 CC BY-NC。商业项目应避免 BY-NC，并为 CC BY 保留作者和链接。[许可 FAQ](https://freesound.org/help/faq/#licenses)
- [Mixamo](https://helpx.adobe.com/creative-cloud/faq/mixamo-faq.html)：角色自动绑骨和动画，可用于个人及商业游戏；不要把角色或动画原文件作为素材重新分发。
- [Game-icons.net](https://game-icons.net/)：大量 SVG/PNG 图标，通常要求按 CC BY 署名。

每下载一个资产，都建议在项目里维护一张表：

```text
名称 | 作者 | 来源 URL | 许可证 | 下载日期 | 是否修改 | 游戏内路径
```

这能避免临近发布时才发现无法证明素材来源。

另外，尽量从一个或两个完整套件中选素材。把十个不同作者的免费资产混在一起，通常会出现“资产拼盘感”，即使每个单独看都很精美。

## 6. 高质量开源游戏和代码

学习 Godot，先看小型、聚焦的项目：

- [Godot 官方 Demo Projects](https://github.com/godotengine/godot-demo-projects)：MIT，约 9.5k stars；最适合查单个功能的标准实现。
- [GDQuest Open RPG](https://github.com/GDQuest/godot-open-rpg)：MIT，约 3k stars；适合学习较完整的 Godot RPG 结构。

学习成熟游戏工程：

- [Mindustry](https://github.com/Anuken/Mindustry)：约 29k stars，适合研究大型内容、模组和跨平台架构。
- [OpenRA](https://github.com/OpenRA/OpenRA)：约 17k stars，适合研究 RTS、数据驱动和网络。
- [Unciv](https://github.com/yairm210/Unciv)：约 11k stars，适合回合制、数据和 UI。
- [OpenTTD](https://github.com/OpenTTD/OpenTTD)：约 8k stars，适合复杂模拟系统。
- [Endless Sky](https://github.com/endless-sky/endless-sky)：约 7.6k stars，适合任务、世界和数据驱动内容。
- [Battle for Wesnoth](https://github.com/wesnoth/wesnoth)：约 6.9k stars，适合战役、关卡和长期内容维护。

许可证注意：

- MIT 通常比较宽松。
- GPL 通常要求分发衍生代码时遵守开源义务。
- MPL 通常是文件级的开源义务。
- 代码许可证不一定覆盖音乐、字体、商标和游戏素材。

所以更适合“阅读和学习模式”，不要直接复制大型代码块进商业闭源游戏。

## 7. 开发游戏真正困难的地方

引擎和编程并不是最难的部分。最常见的问题是：

| 问题                    | 表现                                    | 对策                                   |
| ----------------------- | --------------------------------------- | -------------------------------------- |
| 范围失控                | 不断增加系统、地图、角色                | 为第一款游戏写明确的“绝不做清单”       |
| 玩法并不好玩            | 能运行，但没有继续玩的动力              | 最先做灰盒核心循环，暂时不用正式美术   |
| 内容量低估              | 一个系统需要 UI、音效、教程、存档、测试 | 按完整玩家体验估算，不按代码量估算     |
| AI 产生“看似正确”的代码 | 编译通过但手感、视觉、场景引用错误      | 每次修改后必须运行、截图或录制         |
| 缺少测试                | 修一个地方坏另一个地方                  | 核心规则自动测试，表现层人工试玩       |
| 插件和版本漂移          | 升级后项目无法打开                      | 锁定 Godot 和插件版本，升级走独立分支  |
| 存档被破坏              | 更新后旧档无法读取                      | 从早期就给存档加版本和迁移逻辑         |
| 平台问题                | 手柄、分辨率、Web/移动性能不同          | 每周在真实目标平台构建一次             |
| 没有玩家反馈            | 开发者已经知道怎么玩，发现不了困惑      | 尽早让不熟悉项目的人试玩并保持沉默观察 |
| 营销太晚                | 游戏完成后才发现没人知道                | 垂直切片确定后就准备商店页面和社区     |

开发的核心可以浓缩为：

> 清晰的玩家幻想 + 可重复的核心循环 + 强反馈 + 有意义的选择 + 严格范围 + 持续试玩。

“代码很多”不等于“游戏成立”。

## 8. 适合你的 AI + Godot 工作流

建议采用这个轻量闭环：

```text
一句话游戏概念
→ 3 个设计支柱
→ 明确不做什么
→ 1～3 天灰盒原型
→ 真实试玩并决定继续/转向/放弃
→ 3～5 分钟垂直切片
→ 拆成小任务生产
→ 测试、性能、可访问性
→ 发布
```

每个 AI 任务必须按以下循环执行：

1. 先读取设计目标、相关代码和当前场景。
2. 只实现一个可验证的小变化。
3. 运行解析、编译或 headless 检查。
4. 跑核心逻辑测试。
5. 启动真实游戏。
6. 检查错误日志。
7. 截图或录制结果。
8. 人判断手感、构图、难度和趣味性。
9. 通过后再提交 Git。

项目里建议从一开始就有：

```text
AGENTS.md                AI 工作规则
docs/game-concept.md     一句话概念、受众、核心循环
docs/non-goals.md        明确不做的功能
docs/art-direction.md    美术风格和素材规则
docs/decisions/          关键技术决策
assets/LICENSES.csv      素材许可证清单
tests/                   核心逻辑测试
```

## 9. 你还没有问、但必须尽早决定的问题

开发前至少回答这些：

- 目标玩家是谁？
- 第一发布平台是 Windows、Web 还是手机？
- 2D 还是 3D？
- 单局多长？总游戏时长多长？
- 买断、免费还是纯练习作品？
- 你每周能投入多少小时？
- 最晚什么时候必须完成？
- 哪三个功能是游戏不可缺少的？
- 哪些功能明确不做？
- 美术风格如何保持一致？
- 键鼠、手柄还是触屏？
- 是否需要存档、云存档、本地化？
- 如何获得第一批 5、20、100 名测试玩家？
- 使用 AI 生成的图片、声音或文本是否有可证明的商业使用权？
- 游戏名称、音乐、字体、Logo 是否涉及商标或版权？

如果准备上 Steam，还要考虑：

- 每个产品需要支付 100 美元 Steam Direct 费，调整后收入达到 1000 美元后返还。[Steam Direct 费](https://partner.steamgames.com/doc/gettingstarted/appfee)
- “即将推出”页面至少要在发行前公开两周，实际上应在垂直切片和视觉方向稳定后尽早上线。[Steam Coming Soon](https://partner.steamgames.com/doc/store/coming_soon)
- Steam 要求披露供玩家消费的 AI 生成美术、声音、叙事、本地化等；实时生成内容还要说明安全护栏。[Steam AI 内容调查](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)
- 可访问性不要等最后再补。字幕、键位重映射、字号、颜色辨识、减少屏幕震动等应进入早期设计。[Game Accessibility Guidelines](https://gameaccessibilityguidelines.com/full-list/)

## 最终建议

第一款游戏最好满足这些限制：

- Godot + 类型化 GDScript。
- 单机。
- 2D 或非常简单的 3D。
- 一个核心玩法。
- 10～30 分钟内容，或者单局 5～10 分钟但可重玩。
- 不做开放世界、在线多人、实时服务、用户生成内容和主机首发。
- 先用 Kenney/Quaternius 等成套 CC0 占位资产。
- 第一个可玩版本控制在两周内。
- 完成一款很小的游戏，比搭建一套宏大的“AI 游戏工作室”更重要。

最值得采用的组合是：`Godot + 轻量版 CCGS 阶段流程 + Godogen 的运行证明原则 + headless-godot 的自动验证方法 + 按需插件`。
