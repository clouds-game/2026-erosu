# 色块连落：初版评审与改造路线

评审日期：2026-09-23。基于当前源码和[在线试玩版](https://clouds-game.github.io/2026-erosu/)的桌面浏览器画面；在线版可能晚于或早于本地未提交修改。未验证 Godot 原生窗口的视觉效果。

## 结论

规则代码已经有可保留的基础：完整四连方匹配、整块重力、连锁、三关挑战与学习关卡。但产品入口、规则表达和奖励反馈仍是程序原型。先确定“连锁解谜”为主体验，再围绕一段 3～5 分钟的垂直切片统一重做画面、声音和教学。仅替换按钮贴图不会解决核心问题。

### 优先处理的问题

1. **让玩家先看懂独特规则。** 默认先进入互动学习关，依次教“一个四连方算一块”“三个同色完整方块边相邻”“清除承重块形成连锁”。挑战关放在学会规则之后。当前 `GameController` 和 Web 版都默认 `PuzzleLevels.DefaultLevel`，但学习关在选择框底部。
2. **给消除一个可读的过程。** 落地时点亮将构成匹配的整块外轮廓，短暂停顿后逐块清除、下落、提示连锁层数和得分来源。声音关闭时，视觉仍要能单独传达结果。避免强烈晃屏遮住棋盘信息。
3. **重做视觉层级。** 棋盘应保留中心位置，但目前 10×18 的大片空区和右侧五个等权按钮，让目标、后续块和连锁都不突出。把目标、下一块和分数做成清楚的三级层次；暂停、重开、声音、语言放入一个简洁的暂停/设置入口。移动端单独排版，勿按比例缩小桌面侧栏。
4. **让方块仍然可数。** 这是“数三个完整形状”的游戏。任何贴图、粒子、发光都不能盖掉整块边界。同色相接时，轮廓和辅助符号必须比现在每格的微小标记更易辨认。
5. **缩小双端维护范围。** Godot `GameHud.cs` / `BoardView.cs` 与 Web `App.razor` / `game.css` 各自实现一套界面。先在主平台完成一个切片，再给另一端移植统一的视觉规格；不要两端各自临场设计。

## Godot 插件取舍

先在 [Godot Asset Library](https://godotengine.org/asset-library/asset) 找插件，再按确切需求安装。主工程为 Godot .NET 4.7.2，候选插件需先在独立工作区验证 4.7 和 C# 工程兼容性。

| 插件 | 可解决的问题 | 建议 |
| --- | --- | --- |
| [ThemeGen](https://godotengine.org/asset-library/asset/3299)（MIT，Asset Library 标称 Godot 4.0+） | 用可复用的颜色和样式生成 Godot Theme，减少 `GameHud.cs` 中分散的按钮样式 | **优先试用**，尤其适合新 UI 方向确定后统一视觉。它用 GDScript 生成主题资源，可与 C# 游戏逻辑分开。 |
| [Tween Animation](https://godotengine.org/asset-library/asset/4480)（MIT，标称 Godot 4.5+） | 在编辑器预览多个 Tween 的顺序，用于落地、消除和数字跳动反馈 | **条件试用**：若内置 `Tween` / `AnimationPlayer` 已够用，就无需增加依赖。 |
| [Sparkle Lite](https://godotengine.org/asset-library/asset/5066)（MIT，标称 Godot 4.2+） | 提供 2D 屏幕闪光、Control 缩放、音效池等反馈 | **只做小型验证**。免费版的相机晃动针对 Camera3D；当前棋盘是 Control，不要因插件而改架构。 |
| [Godot AI](https://godotengine.org/asset-library/asset/5050)（MIT，标称 Godot 4.5+） | 让 AI 操作编辑器和截取运行画面 | 开发效率工具，**不负责视觉质量**。已有 CLI/截图闭环能工作时再考虑。 |

Godot 本身已有 [Theme](https://docs.godotengine.org/en/stable/tutorials/ui/gui_skinning.html)、[Tween](https://docs.godotengine.org/en/stable/classes/class_tween.html) 和 [AnimationPlayer](https://docs.godotengine.org/en/stable/tutorials/animation/introduction.html)，不应为每个小动效引入一个插件。

## 实施顺序与验收

1. **产品切片**：明确挑战/自由模式谁是主入口；写出前三分钟的教学脚本与连锁奖励脚本。只做一个学习关和一个挑战关的完整体验。
2. **美术选型**：选 A/B/C 后，下载少量候选，制作同一局面的对比画面。冻结字体、颜色、方块轮廓、UI 间距和特效强度，再批量导入。保留素材许可清单。
3. **表现层改造**：先重做 Godot 端的棋盘、HUD、结算和暂停设置；接入选定音效、输入图标与反馈动效。规则层保持独立，除非试玩证明规则本身需要改。
4. **玩家验证**：找至少 5 名没读过文档的人试玩。看他们能否说清“消除三个完整方块”，能否预测一次连锁，并发现卡住的位置。用录像/观察改教学和反馈。
5. **Web 同步**：主端切片过关后，再按同一视觉规格处理 Web。核对小屏、触屏和键盘操作；只做真实行为验证，避免堆叠重复测试。

进入全面制作前，先确认视觉方向 A/B/C，以及主平台是 Godot 桌面还是 Web。两项决定会直接影响素材格式、UI 布局与先改哪套表现代码。
